# Opening critical wind-up · training-only protocol

Test whether skipping the critical wind-up for one opening proposal improves the chance of the bot landing first. Both arms freeze the same saved model (`6b167faf6d664abf34158fe125dff337011c4679f1ef7a9fb0a179610abf30e6`) and use the same controller revision and settings as the [opening replication](combat-opening-replication-result.md). Earlier fights supply no rows to this study.

Run 12 fresh matched pairs in this order: `14529115, 14530703, 14433366, 14510738, 14095068, 14656474, 14594426, 14804545, 14463827, 14783290, 14360586, 14121260`. Use `random.Random(170214).sample(range(14_000_000, 15_000_000), 12)`. Rotate order between existing-first and grounded-first, starting with existing. Use the existing isolated Normal arena, adult unarmed zombie, full HP and food, iron sword and armor, and no shield. Start geometry and yaw are matched. Zombie behavior and the timing of server ticks can differ. Run one fixture and one inference CPU thread, with the existing 18-minute budget checked between fights.

Both arms submit action 6 once at the first observation with a present, visible target within three blocks, weapon equipped, cooldown ready, and the bot grounded. The existing arm uses native combat as written. The grounded arm disables `critical_hits` only for this call to the native attack helper. Check actual footing at handoff in both arms. A loss of footing at handoff is recorded as a refusal and uses up the opening; no second attempt. Keep native re-aim, reach, sight, cooldown, ownership, weapon and health checks. Return to the frozen model the next decision, including native critical behavior. No-trigger fights, refusals, and starts on which the existing helper chooses a grounded swing remain in their assigned arms.

Use fight-level bot-first outcome and the [same native receipts and ambiguity rules](combat-opening-protocol.md). The bot must have a confirmed owned-target hurt earlier than the first bot health loss. Close receipts (≤50 ms), conflicting owned-mob native packet order, and wins with a missing target-hurt receipt remain ambiguous. Use client receipt timings, which cannot establish the exact server tick. Score all valid paired starts and resolve ambiguity in favor of the existing helper for the gate. Pass only with all 12 pairs, at least three net additional confirmed bot-first hits (+25 percentage points conservatively), mean total HP lost at or below existing, wins at or above existing, and deaths and escapes at or below existing.

Report every start and both arms, including attack proposal, native request, attributable first target hurt (only one preceding recorded request), first bot damage, confirmation delays, helper refusal, whether a native critical wind-up actually started, gross damage, deaths, wins and escapes. Keep events where attribution is unavailable visible. Use the frozen-state dashboard check with at most two 250 ms backoffs after 1.5-second request timeouts. Preserve native post-release stop rules. End the block on exhausted checks, invalid fixture/telemetry, intentional stop, or health limit, retain any completed fights, verify cleanup, and label the experiment incomplete. No resetting or repeating released fights.

If the gate passes, use pre-action features and trace-derived outcome labels to propose a small three-arm development test of a learned choice, including both fixed opening helpers. If the gate fails, close the hypothesis for this setup and use the opening traces to identify the largest remaining source of late or unconfirmed hits. Keep production and the reserved holdouts untouched.
